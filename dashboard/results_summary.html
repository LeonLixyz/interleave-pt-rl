Does inserting RL between pretraining stages help?

A controlled study on a 47M chess model: every combination of pretrain → RL → pretrain, with the RL contribution carried either as weights or as verified traces (data). All numbers are pass@k on the same fixed 53,157-puzzle evaluation, 16 samples per puzzle.

Setup (shared by every experiment)

Model
47,245,312-parameter Qwen3: 12 layers, hidden 512, 8 query / 4 KV heads, context 3,072, custom 85-token chess tokenizer (moves + <T>, </T>, <sep>, <call_env>).
Pretraining
Chess game corpus; "5B" / "10B" = tokens consumed. SFT rows (supervised puzzle-solving traces, 77,717 total) are mixed into the pretraining stream as individually masked examples at loss weight 1.0 — except the "no SFT mixed → SFT-stage" recipe, which trains pure pretraining first and a separate 3-epoch SFT stage after. AdamW, cosine 1e-3 → 1e-5, batch 168 × 3,072 tokens, 8×H200.
RL
GRPO on 53,225 chess puzzles: 256 prompts × 8 samples per update, lr 1e-5 unless stated, KL 0.001, temperature 1.0. Multi-turn: the model may call a move-verification environment up to 6 times per answer.
RL data settings
  • all — every drawn prompt trains.
  • filter — on-policy dynamic filter: keep only prompt groups where some of the 8 samples succeed and some fail; redraw the rest.
  • solvable-only — offline pre-filter: the 26,967 puzzles the starting checkpoint solved 1–15 times out of 16 in its own evaluation (removes never-solved and always-solved).
Verified traces
The trace generator was sampled exactly 16× per puzzle; every sample was scored by the reward function. From the correct, format-valid, distinct samples of each puzzle, up to k were kept ("sample 16, verify, keep ≤ k"). Traces were tokenized with the same masking as SFT rows and mixed into the pretraining stream.
Weight change
Two measures between the RL endpoint and the checkpoint RL started from. weight Δ (L2): relative L2 distance, ‖θafter − θbefore‖₂ / ‖θbefore‖₂ over all parameters. params changed: fraction of the 47.2M parameters whose stored bf16 value differs at all — updates smaller than bf16 resolution round away, so this counts parameters that moved enough to persist. For scale: one 5B pretraining leg gives L2 ≈ 50% and changes essentially every parameter.
Held-out PT loss
Cross-entropy on 6.3M held-out pretraining tokens (2,048 packed 3,072-token windows from corpus shards the frozen 10B training selection never used).
Evaluation
53,157 prompts (68 overlong excluded) × 16 samples, temperature 1.0, prompts prefixed with <bos> exactly as in training; pass@k via the unbiased estimator; scored by the training reward function. Same evaluator for every row.

At lr 1e-5, RL sharpens pass@1 by ~4 points, never grows pass@16, moves only 0.2–0.4% of weight mass, and leaves the held-out PT loss essentially untouched. At lr 1e-4 the weights move 4.0%, pass@1 triples — and the PT loss visibly degrades (0.501 → 0.549), a real LM cost that the next pretraining leg fully heals (table C). The two-stage SFT rows sit at much higher PT loss (0.89) because their pretraining stopped at the 1e-4 floor and the SFT stage moved them off the game distribution.

F. Second-round RL: interleaved (traces) vs pretrain-then-RL

Four models, each given the identical RL recipe on top of its own base. The question: after spending the same 10B pretraining tokens, is a model whose pretraining data included verified traces from an earlier RL round a better starting point for RL than a conventionally pretrained model?

The four experiments

Named here once, used in the table and every curve below. Each name is one complete chain; every stage is written with its settings.

  • interleaved (rollout traces) — 5B-pretrain → RL(solvable-only, 1e-4, 1,500) → harvest all 1,592,352 distinct verified-correct trajectories that this RL run wrote to disk during its own training (no extra generation) → second 5B pretraining leg with those traces mixed in (19,398 steps vs the control's 9,920, because the traces add tokens; checkpoint tracep2roll/final, 38.4% pass@1) → RL(own solvable-only set, 1e-4, 1,500). Endpoint rl_hf/rollband-lr1e4-rl1500-s1500.
  • interleaved (eval traces, k=16) — same first RL run, but the traces come from a separate evaluation pass: the RL model was sampled 16× per puzzle and every verified-correct, format-valid, distinct sample was kept (307,648 traces after tokenization filters) → second 5B leg with those traces (11,751 steps; checkpoint tracep2k16/final, 34.8% pass@1) → RL(own solvable-only set, 1e-4, 1,500). Endpoint rl_hf/k16band-lr1e4-rl1500-s1500.
  • pretrain-then-RL (10B, one run) — 10B-pretrain in one run (row 2 of table A, 14.8% pass@1) → RL(own solvable-only set, 1e-4, 1,500). Endpoint rl_hf/e2w1band-lr1e4-rl1500-s1500.
  • pretrain-then-RL (10B, two runs) — 10B-pretrain as two 5B runs with an optimizer reset between them (row 3 of table A, 15.1% pass@1) → RL(own solvable-only set, 1e-4, 1,500). Endpoint rl_hf/e3p2band-lr1e4-rl1500-s1500.

The shared RL recipe

  • GRPO, 256 prompts × 8 samples per update (2,048 rollouts/update), 1,500 updates, fresh optimizer, constant lr 1e-4, KL coefficient 0.001, temperature 1.0, multi-turn with up to 6 environment calls, checkpoint every 40 updates.
  • Each run trains on its own solvable-only set: the puzzles the starting checkpoint solved 1–15 times out of 16 in its own full evaluation — an offline pre-filter built once before RL, then fixed for the whole run (this is not the on-policy dynamic filter). The next table shows each set and where it comes from.
  • Budget: all four spent the same 10B pretraining tokens and get the identical 1,500-update RL run here. What is not matched: the interleaved runs carry an earlier RL round of 1,500 updates (3,000 total RL updates vs 1,500), and interleaved (eval traces) additionally spent one 16-sample generation pass to produce its traces, and the trace tokens lengthen the second pretraining leg (+18% steps for eval traces, +96% for rollout traces). The equal-total-RL controls extend both pretrain-then-RL runs to 3,000 updates: the one-run control is finished (in the table); the two-run control is training.

The loop applied to the 10B models

The same collect-and-distill cycle, run on top of the two pretrain-then-RL models from the table above. Every verified-correct trajectory each model's RL run wrote during training was harvested (1,269,157 usable traces from the one-run model — 25.5% of its positives failed the format quality gate, its format damage showing up in its own rollouts; 1,615,462 from the two-run model, 0.07% rejected) and mixed into a further 5B pretraining leg built from corpus shards the frozen 10B selection never used (same recipe as the interleaved runs' second leg: fresh optimizer, cosine 1e-3 → 1e-5, the second SFT half; 17,470 / 19,529 steps), initialized from the plain 10B checkpoints — the RL round contributes data only. Then one more RL round: 1,500 updates, lr 1e-4, each on the new endpoint's own solvable-only set (27,906 / 26,836 puzzles).

Budget note: these chains have 15B pretraining tokens (vs 10B everywhere else in this section) and 3,000 total RL updates. Nothing else in the study is token-matched to them; they answer "does the loop keep working?", not a controlled comparison.

Curves

How each curve is measured:

  • Training reward — the mean score of the 2,048 on-policy samples of every update, read from the run's saved rollout files; plotted as a 15-update moving average sampled every 10 updates. Rewards are computed on each run's own solvable-only set, so levels are not comparable across runs: the expected starting reward (the base model's mean win rate over its own set) is 53.3% / 49.5% / 24.6% / 25.1% for the four experiments in table order. Reward growth within a run is what to read, not the gap between runs. In every panel, the pretrain-then-RL curves continue past the dashed line at update 1,500 where data exists: these are the equal-total-RL controls, resumed from the 1,500-update checkpoint with full optimizer state and still training toward 3,000. The interleaved runs stop at 1,500 because their other 1,500 updates were spent in their first RL round.
  • Held-out pretraining loss — cross-entropy on the fixed 6.3M-token held-out set (same as every other table), measured on the checkpoint at every 200th update (converted to HF format) plus both endpoints.
  • SFT loss — cross-entropy on the answer (supervised) tokens of a fixed sample of 4,096 SFT rows (2,048 from each half of the SFT set; the same fixed sample as every SFT-loss number elsewhere on this page), measured at the same checkpoints. It asks: how well does the model still predict the supervised solution traces it was pretrained with? Rising SFT loss means RL is moving the policy away from that supervised solution style.
  • pass@1 / pass@16 — at every 200th update, an evaluation on a fixed 1-in-8 subset of the benchmark (6,645 prompts × 16 samples); at updates 0 and 1,500, the full 53,157-prompt evaluation. Subset points wobble roughly ±0.5 points relative to full evaluations.

Training reward: every run climbs steadily and none has plateaued by update 1,500 (per-update means there: 79.1% / 72.2% / 66.4% / 65.4% in table order), and the extended one-run control keeps climbing past 1,500 (48.2% pass@1 at update 2,800) — final rows join the table at 3,000. The two-run control's first extension was discarded: around update 1,950 its rewards collapsed to near zero for ~40 updates while format stayed intact (an infrastructure failure, not a policy signal), and training on those batches at lr 1e-4 measurably damaged the model (held-out PT loss 0.505 → 0.66 by update 2,200). It was relaunched from the 1,500-update checkpoint with full optimizer and data-sampler state. Note that pretrain-then-RL (one run)'s format rate on its own training rollouts stays ≥99.8% throughout — its 86.7% format rate is measured on the full held-out evaluation, so the format damage is concentrated on puzzles outside its RL training set.

Held-out PT loss: all four degrade as RL progresses — lr 1e-4 RL always costs language-modeling quality — with roughly a third to a half of the total cost paid in the first 200 updates, decelerating after. The interleaved runs pay the least overall (+0.018), pretrain-then-RL (one run) the most (+0.028), and the loss ordering mirrors the format outcome. For scale, the first-round RL on the 5B base cost +0.048; and table C shows a subsequent pretraining leg heals this cost completely.

SFT loss: the interleaved bases start ~0.03 higher (0.531/0.536 vs 0.505) — the style displacement from mixing traces into pretraining, already noted in table D. During RL every run moves further off the supervised style, but pretrain-then-RL (one run) moves most (0.505 → 0.752), again mirroring its format damage; the interleaved runs end lowest (0.632/0.652) despite RL-ing just as hard. Rising SFT loss with rising pass@1 is expected — RL replaces the supervised solution style with its own — but the size of the rise tracks how much collateral damage the run does.

pass@1: the interleaved runs start 20+ points ahead and are never caught. The pretrain-then-RL runs improve faster in absolute points per update (they have more headroom — their sets contain more unsolved puzzles), but the ordering of the four runs is unchanged from update 200 onward.

pass@16: the interleaved runs hold coverage flat to slightly up (rollout traces 61.0% → 62.0%). Pretrain-then-RL (one run) first loses coverage — 60.1% at update 0 down to 57.4% at update 200, well beyond subset noise — and needs ~1,200 updates to climb back to where it started; the two-run variant shows the same dip more mildly (59.0% at update 400). So at lr 1e-4, RL initially converts coverage into first-try accuracy and only later re-earns it. The interleaved runs skip that regression entirely — their coverage was consolidated by the trace pretraining leg — and end where the pretrain-then-RL runs merely recover to (~61.5% vs 62.0%).

Conclusions

  • Do not interleave RL into pretraining. RL weight changes are overwritten by subsequent pretraining regardless of their size; at equal compute the interleaved model ends strictly below the pretrain-then-RL model.
  • To carry RL ability through more pretraining, distill it into verified traces. Traces mixed into the stream retain the knowledge, scale with dosage, and restore the diversity RL sharpening consumes — the traces can be harvested for free from the RL run's own saved rollouts.
  • The RL learning rate dominated every other design choice. 1e-5 (the historical default) capped RL at ~+4 pass@1 with zero coverage gain; 1e-4 tripled pass@1 and produced the first real coverage growth, with no format collapse.
  • The loop iterates, on any base. Two rounds of (pretrain on traces → RL) took the same 5B ancestor from 10.2% to 51.4% pass@1, 8–11 points above conventional 10B-pretrain-then-RL with the identical RL recipe. Applied on top of the 10B pretrain-then-RL models themselves (one further free-trace pretraining leg + one RL round), it reaches 54.6% / 52.9% pass@1 and 65.7% pass@16 — the best numbers in the study — while also improving held-out language modeling.
  • Dynamic nonzero-variance filtering is a consistent but small win (~+1 pass@1); one-vs-two-cosine schedule splits are irrelevant everywhere they were tested.

Caveats

  • One seed per cell (a reseed replication existed only for one earlier ablation arm).
  • Pretraining used bf16 parameter storage, which froze all RMSNorm scales at 1.0 in every run — shared by all arms, so comparisons hold, but absolute numbers may improve with fp32 master weights.
  • The second pretraining leg re-warms the learning rate to 1e-3; a low-lr continuation might preserve more RL signal (untested).
